# Framecheck Local 桌面功能评估与多状态交付实施方案

日期：2026-09-24  
状态：待用户审查，仅文档，不授权实施代码

## 1 背景与目标

Framecheck Local 已有本地 PSD/PSB 转换、Bundle 看稿和 Vue 静态页导出。近期目标是让前端开发在内部项目中稳定完成「PSD/PSB → 可用交付包 → 核对状态与资源」。主要交付目标是移动 H5，同一 PSD 的隐藏图层或组通常保存按钮的其他视觉状态。

本次讨论已确认：首版覆盖按钮与可点击切图；工具提供 H5 状态和转换模板，前端逐组件确认或修改；希望每页人工确认约五分钟；缺状态时警告并允许带记录交付；状态资源和转换规则随 Bundle 交付；看稿台能点击演示同一组件内部的状态转换；首版不要求导出的 Vue 页面执行交互；桌面端近期希望是可安装的 Windows 程序。

新增约束：多状态能力必须可关闭，关闭后现有转换、看稿、普通切图、Vue 静态页导出与旧 Bundle 行为保持可用。新能力以显式启用和版本化契约接入，不能强迫既有交付流程先补状态标注。

这里的「多状态机」具体指组件局部的**视觉状态、资源映射及事件转换**。首版不做跨组件编排、弹窗联动、页面跳转或通用状态图编辑器。

## 2 事实、判断与证据边界

| 类型 | 内容 |
| --- | --- |
| 事实 | Tauri 已桥接转换任务、取消、进度和打开输出目录。工作区当前 `tauri.conf.json` 已启用 NSIS 并声明 `psd2code-runtime` 资源，本地也存在 runner 文件；尚无已安装程序在独立机器成功转换的验证记录。 |
| 事实 | `JobManager` 使用内存 `HashMap` 保存任务，`list_recent` 读取该内存；重启后不具备任务记录恢复机制。 |
| 事实 | Bundle 现为严格的 `1.0.0` 契约，只包含设计事实、可见切图、参考图和诊断，没有状态字段。 |
| 事实 | 上游 `psd2code` 能发现隐藏的已标记层并生成 `hidden_marked` 诊断，但设计节点和资源导出都只遍历可见层。 |
| 事实 | 真实样本 `long-mobile-page` 的四条隐藏标记诊断同时包含季节内容和两个同名报名按钮。名称与隐藏性不足以证明组件归属。 |
| 事实 | Vue 导出根据名称启发式生成静态按钮占位，不生成状态转换逻辑。 |
| 事实 | 导入缓存目前按 `[sourceSha256+portableSchemaVersion]` 查找；同一 PSD 的不同状态标注如果都用 `1.1.0`，会误命中旧缓存。 |
| 事实 | 当前 ZIP 校验仅允许既有五个固定工件与 `assets/*`；导入 Worker、仓库打开逻辑也固定读取这五个工件。资源清单声明的 SHA-256 尚未与实际资源字节逐一比对。 |
| 判断 | 只给看稿台添加状态标签或图片切换不能减少隐藏态切图缺失；必须把源层识别、资源导出、必需状态确认与审计连成一条路径。 |
| 待验证 | 候选识别能否在代表性 PSD 上把人工确认压到每页约五分钟，隐藏组的像素导出能否忠实保留效果与遮罩。 |

本次只审阅本地代码、文档和真实 Bundle 样本，未构建或运行测试。外部官方网页浏览被自动审批超时拦截，因此不使用未经核实的竞品比较作为优先级依据。`PRODUCT.md` 仍按纯 Web 工具描述产品，应在实施时同步到当前桌面能力。

## 3 多角度功能优先级

| 功能 | 用户价值 | 实现代价与风险 | 建议 |
| --- | --- | --- | --- |
| Windows 安装包与 runner 随包交付验收 | 内部用户能脱离开发环境稳定转换真实 PSD | 中；配置已开始落地，仍需发布编译、版本、路径和安装后验证 | P0 交付前提 |
| 组件状态资源与交互覆盖 | 直接针对隐藏状态资源遗漏，可在交付前看到可运行的局部交互 | 高；跨 Python 转换器、Bundle、Tauri、看稿台 | P1 核心新增 |
| 桌面任务持久化与重新打开产物 | 重启后可核查结果、失败和输出目录 | 中；需失效产物与隐私处理 | P1 稳定性 |
| 保存转换参数预设 | 减少重复输入和参数漂移 | 低到中；需按真实任务验证预设 | P1 日常效率 |
| 批量 PSD 转换与失败汇总 | 多页面交付时减少重复操作 | 中；使用频率尚无证据 | 待访谈确认 |
| 拖入 PSD、文件关联与系统右键入口 | 缩短开始转换的步骤 | 低到中；不解决缺资源 | P2 |
| 设计修订差异检查 | 比较两次交付的状态与资源变化 | 高；需跨版本身份映射 | P3 |

建议先把 P0 的可安装交付做成稳定基线，再做多状态闭环。通用状态图编辑器、AI 自动判定必需状态、云协作和 Photoshop 式编辑暂不进入近期范围。自动判断无法知道某个业务按钮是否真的需要禁用态。

## 4 首版用户流程

1. 前端在桌面端选择 PSD/PSB，可打开「检查交互状态」开关。关闭时直接执行现有转换流程；开启时进入预扫描。扫描返回可见与隐藏候选层的稳定 ID、层级、名称、边界、可见性和标记，不修改源文件。
2. 系统把可点击元素和隐藏层按名称、层级、几何邻近性给出候选关系，并显示每条建议的依据。候选始终是「待确认」。
3. 前端逐组件确认初始状态、必需状态、状态对应图层和事件转换。可套用常见 H5 模板，再逐项删改或标为不适用。歧义候选需要显式处理。
4. 转换器导出已确认状态关联的源层或组：默认态优先复用现有切图，若没有切图则导出前端明确选择的可见层；其他状态可来自隐藏层。普通参考图和现有可见切图语义保持原样。转换器记录状态资源文件、尺寸、像素哈希及源层身份。
5. 看稿台在选中组件后展示局部交互预览。点击或按下预览控件，根据 Bundle 中的转换规则改变状态并使用对应资源；同时展示当前状态、触发事件和缺失提示。
6. 导出前显示组件覆盖摘要。缺失资源、渲染失败、不可达状态和待确认映射均有明确记录。允许继续交付，但 Bundle 中保留警告，另一台机器打开时仍可复核。

**界面边界：**首版用独立的组件局部预览演示转换。不要直接在整页 `reference.png` 上覆盖另一状态图片并声称它是准确的整页渲染，因为原图已有默认状态像素且其他状态的边界可能不同。画布仍可定位原组件，局部预览负责可信的状态演示。

## 5 状态、事件与覆盖语义

### 5.1 模板和运行规则

移动 H5 的起始模板建议提供：

| 模板 | 默认状态和事件转换 | 适用范围 |
| --- | --- | --- |
| 瞬时按压 | `default` 经 `pointerdown` 到 `pressed`，经 `pointerup` 或 `pointercancel` 回 `default` | 有按压视觉反馈的普通按钮 |
| 选中切换 | `default` 经 `click` 到 `selected`，`selected` 经 `click` 回 `default` | 开关或页签式控件 |
| 禁用展示 | `disabled` 不响应点击，仅由预览面板显式选择或重置 | 有禁用资源的按钮 |
| 加载展示 | `click` 可到 `loading`，返回条件必须由前端显式定义 | 确实存在加载态的控件 |

模板只是起点，不默认要求每个按钮有 `pressed`、`disabled`、`selected` 或 `loading`。触屏 H5 不默认要求 `hover`。首版每个组件只有一个当前状态，不自动组合「选中且按下」等复合状态；如业务必须组合，需显式建状态并关联资源。

预览以 Pointer Events 表达鼠标和触屏按压，键盘用 Enter/Space 触发等价操作；`pointercancel` 和离开控件时不能永久卡在按压态。看稿台的「切换到指定状态」是审稿命令，与实际用户事件区分显示。没有后端或计时逻辑时不得自动伪造加载完成。

### 5.2 审计结果

| 结果 | 判定 | 行为 |
| --- | --- | --- |
| 未定义 | 组件尚未确认必需状态及事件规则 | 不计为完整 |
| 待确认 | 自动候选存在多义性或没有人工确认 | 展示候选依据 |
| 完整 | 每个必需且可达的状态都有校验通过的资源，转换目标合法 | 可运行局部预览 |
| 缺失 | 必需状态无映射、渲染失败、文件缺失或哈希不符 | 指明组件和状态，警告并允许交付 |
| 不适用 | 前端明确排除某状态 | 保留声明，不计为缺失 |

需校验：初始状态存在；每条转换的起点、事件和目标合法；同一起点与事件不得出现两个无条件目标；要求演示的目标状态必须可达；每个必需状态资源存在且可读；同一组件源层映射不能互相矛盾。声明之外的业务状态无法被工具发现，因此「完整」只表示已确认需求的覆盖完整。允许缺状态的交付物应把该状态保留在 `states.json` 中，省略资源引用并记录失败原因；不得写入一个指向不存在文件的假 `assetId`。

## 6 技术契约草案

本节是实施建议，字段名和版本在编码前需以两到三份真实 PSD 校准。首版需要跨两个仓库实施：本仓库 `framecheck-local` 与 `D:/proje2/psd2code`。

### 6.1 上游扫描与隐藏状态导出

- 扩展 `scanner.py` 的隐藏候选记录，提供稳定源层 ID、父 ID、顺序、原始名称、层级路径、边界、标记、可见性链和候选原因。现有 `hidden_marked` 诊断只有名称与路径，不能作为稳定关联键。
- 加一条只读预扫描入口。预扫描和最终转换使用同一套源层身份算法；源 PSD 变化后，旧标注标为待核对，不能静默套用到新文件。
- 给 `assets.py` 增加按确认的源层 ID 导出隐藏状态的路径。只渲染显式映射的层；正确处理组内可见性、遮罩、效果、裁切、嵌套标记和透明边界；异常与取消后恢复内存中的原可见性，绝不保存回 PSD。
- 默认状态优先复用现有 placement 的资源；没有 placement 时可导出前端明确选择的可见层。隐藏态即使没有原有 `-h-` 标记，只要经过前端显式确认，也可作为状态专用资源导出；未确认的未标记图层仍不自动导出。状态资源不能混进普通可见切图列表或改变 `reference.png`。
- 对源层不存在、空像素、资源重复、渲染失败和边界不一致分别报告诊断，禁止生成一个看似完整的空状态。

### 6.2 桌面请求和标注持久化

- 在 `src-tauri/src/lib.rs` 和桌面桥接中增加结构化预扫描与状态确认请求；沿用现有 runner 固定路径、受控参数、进度与取消模式，不接受界面传入可执行文件或任意 CLI 参数。状态关闭时继续使用现有协议和执行路径；状态开启时使用扩展协议，不能在旧请求上悄悄改变必填字段。
- 前端标注先存在本机侧车清单，以源文件 SHA-256 和源层 ID 关联；记录确认者可选、时间、组件状态与事件规则。PSD 原件始终只读。
- 重新预扫描同一 PSD 可恢复标注；源哈希变化时进入重匹配检查，失踪或歧义映射必须重新确认。侧车清单不是最终交付真值，生成 Bundle 后应把确认结果写入包内。
- 错误和进度需区分扫描、等待确认、隐藏态渲染、Bundle 校验与完成，避免一个笼统「转换失败」。

### 6.3 Bundle 版本和数据结构

建议状态功能开启时使用新契约 `1.1.0`，在新版 `bundle.json.artifacts` 中声明必需的 `states.json`，即使没有组件也写空集合；功能关闭时仍输出现有 `1.0.0` 结构，不加入 `states.json`。旧 `1.0.0` 继续可导入，并明确显示「没有状态交付数据」。新版空集合表示「已启用但没有确认组件」，不能算覆盖完整。不能直接在严格的现有 `1.0.0` `bundle.json` 中添加字段而不升级校验器。

`states.json` 至少包含源 SHA-256、组件 ID 和名称、默认可见节点 ID、初始状态 ID、状态数组、必需或不适用声明、源层 ID、可选资源 ID、预览边界、转换数组、确认状态和诊断。转换采用显式 `{from,event,to}`，不通过图层名猜测。资源字节继续由 `assets.json.assets` 声明并校验哈希；状态引用资源 ID，普通 placements 与状态引用分开，看稿台普通切图列表过滤仅供状态使用的资源。

新导入器需要按版本解析 `bundle.json` 与工件白名单，检查 `states.json` 来源哈希、组件与状态唯一性、转换引用、资源文件存在性、路径安全和实际字节 SHA-256。对旧包不显示缺失警告，因为旧包没有状态需求数据；应显示「未定义」。Bundle 一经生成仍是不可变交付物，本机标注变更通过重新转换生成新包。

**缓存身份必须同步升级。**现有 IndexedDB 索引只看 PSD 哈希与 schema 版本，会把同一 PSD 的不同状态声明当作相同 Bundle。建议为 `1.1.0` 增加构建指纹：由生成器对规范化状态声明、资源清单及参考图哈希生成，写入 `bundle.json`；导入索引使用 `[sourceSha256+portableSchemaVersion+buildFingerprint]`。旧 `1.0.0` 保留原索引兼容查询，Dexie 升级数据库版本并迁移既有记录。重新标注或重新渲染后即使 PSD 未变也应产生不同指纹；重复导入同一包仍命中缓存。指纹应由实际产物内容计算，不能只用标注时间。

现有 `resolveBundleStatus` 只区分原有资源导出错误和普通诊断。状态覆盖结果应单独投影为 `stateCoverage`，避免一条允许交付的状态警告改变旧 `ready/partial` 的既有语义。旧 Bundle 该字段为 `unavailable`，不能被错误地标成完整。

### 6.4 看稿台交互

- 在开发元素或 Inspector 中提供「显示状态检查」开关；关闭时隐藏新增的状态入口、局部预览与状态叠加，原有画布选择、测量、资源列表和原始图层树按现状工作。开启且 Bundle 为 `1.1.0` 时按组件列出默认、其他状态、当前状态、资源、转换和警告。
- 局部预览读取 Bundle 声明的状态资源，不重建 PSD；状态变更由纯状态转换函数驱动。预览支持指针、触屏、键盘和显式重置，缺资源时显示失败态而不是旧图片。
- 预览与画布定位使用同一个组件源节点关联；隐藏层没有现有 `design.json` 节点时，使用 `states.json` 中的稳定来源及边界，不制造普通可见节点。
- Vue 静态页导出首版仍按现有可见切图生成静态页面；若 Bundle 含状态规则，导出预览明确提示这些规则和状态资源尚未写入目标 Vue 项目。真正生成 Vue 交互及其资源复制需另立目标项目组件与事件契约。

### 6.5 开关与回归隔离

| 场景 | 预期行为 |
| --- | --- |
| 转换页开关关闭，默认值 | 不运行状态预扫描，不要求人工确认，沿用协议 1 与现有导出路径；输出结构仍为 Bundle `1.0.0` |
| 转换页开关开启 | 运行预扫描和确认，走扩展协议，输出 Bundle `1.1.0`；警告不阻止用户交付 |
| 已开启的转换任务进行中 | 开关锁定为该任务的快照；若要改动，取消并重新发起，不在任务中途混合两套契约 |
| 看稿页显示开关关闭 | 仅隐藏状态检查 UI，不删除状态数据，不改变原有画布、切图或 Vue 导出 |
| 看稿页显示开关开启，但打开旧 Bundle | 显示「该交付包没有状态数据」，不伪报缺失，也不尝试从图层名自动补造 |
| 看稿页显示开关开启，打开新 Bundle | 显示已校验的状态、转换及缺失记录，可运行局部预览 |

转换设置和看稿显示是两个不同开关：前者决定是否生成状态资源，后者只决定是否展示状态能力。两者可分别保存在本机偏好中，但默认关闭，且不能改变已生成 Bundle 的内容。这里的「随时关闭」指看稿时可即时隐藏；已启动的转换无法在不重做产物的情况下中途改变模式。

回归门槛：对现有真实 PSD 在关闭状态功能时，Bundle 文件集合、版本、可见 placement、切图数量、诊断、看稿结果和 Vue 静态页导出应与原流程一致。旧 `1.0.0` 的导入、缓存、删除、导出与原有画布操作都要通过既有回归测试。新 `1.1.0` 的状态专用资源不能泄漏到普通切图计数、批量下载或画布命中测试中。

### 6.6 数据流和示例契约

```text
PSD/PSB
  -> runner 预扫描候选 -> Tauri 结构化结果 -> 前端确认组件与规则
  -> 本地侧车清单 -> runner 按清单导出隐藏态资源
  -> Bundle 1.1 states.json + assets.json -> 看稿台校验 -> 局部交互预览
```

下面是 `states.json` 的**说明性示例**，字段以契约 POC 结果为准。`sourceLayerId` 来自全量 PSD 扫描；隐藏层不要求出现在仅含可见节点的 `design.json`。`assetId` 必须能在 `assets.json.assets` 找到，且文件能通过路径与哈希校验。

### 6.8 协议与文件落地细节

当前 Rust `StartJobRequest` 使用 `deny_unknown_fields`，Python `DesktopRequest` 只接受 `protocolVersion: "1"`。推荐让关闭状态功能的请求保持原样；为开启状态的转换新增协议 2 请求，并为预扫描定义独立的协议 2 操作。两个版本在入口按版本分派，不让旧 runner 收到额外字段，也不把状态标注编码进自由文本参数。状态计划在 Rust 写入受控 `request.json` 后由 runner 读取，Rust 验证源路径、任务 ID、计划大小、组件与状态数量以及状态标识。

预扫描应写 `candidates.json` 到当前任务私有 staging，runner 只在事件里回报工件类型和相对标识，由 Rust 在已知 staging 根下解析、限制大小并读取后再返回 Vue。现有 `runner.rs` 对 stdout 单行最多保留 64 KB，并会清洗日志；把整份图层树放进 JSONL 事件会截断。不要将任意 runner 返回路径直接交给界面读取。建议先以 16 MiB 作为扫描报告上限，并用真实最大 PSD 验证该上限是否足够。

`DeliveryBuilder.build` 当前对同一 PSD 实例执行设计分析、普通资源导出、令牌、报告、打包。状态开启时应在普通资源导出后、`write_archive_from_artifacts` 前插入隐藏态资源导出与 `states.json` 生成；关闭时不进入新增阶段。`pack_design_bundle` 和桌面 `DeliveryBuilder` 都会调用打包逻辑，必须保证状态关闭的 CLI pack 与桌面转换继续产生五个既有工件。`design.json` 和 `assets.json` 有各自的内部 schema 版本，不能把它们与便携 Bundle 的 `1.0.0/1.1.0` 版本混为一谈。

侧车清单推荐放 Tauri 应用数据目录，按源 SHA 命名，写入时用同目录临时文件加原子替换。关闭功能不删除既有标注。启用时若源哈希变化，只显示旧标注的重匹配建议；无匹配或多义匹配不自动确认为已审核。取消任务时清理任务 staging，保留源 PSD、之前已交付的 Bundle 和人工标注。

### 6.9 导入、缓存和资源统计接入点

`src/features/bundle/archive-validation.ts` 的白名单、`src/features/importer/bundle-import.worker.ts` 的固定读取与 staging 工件数组、`src/features/bundle/bundle-repository.ts` 的打开逻辑都需要按 1.0/1.1 分支处理 `states.json`。新版状态资源仍写在允许的 `assets/*` 路径内，不放宽 ZIP 路径、软链接、加密条目、单文件、总解压量或条目数限制。增加的状态图片会占用现有 512 MiB 解压限额，超过限额时应给用户明确失败信息，不能悄悄丢弃状态资源。

`src/features/storage/indexeddb-index.ts` 需要 Dexie 版本迁移、新指纹索引和旧记录兼容查询；`LocalBundleRecord` 与 `PortableBundleSummary` 要携带新指纹。当前 `bundle-repository.ts` 先查缓存再解压，因此新指纹必须在 Worker 准备阶段从新版清单读到。若旧记录没有指纹，仅按旧版路径查询；新包不可退化到源 SHA 加版本的旧查询。Bundle 导出应保留 `states.json` 及状态资源原始字节。

当前 `bundle-adapter.ts` 会遍历 `assets.json.assets` 生成普通资源列表。新版要以普通 `placements` 与 `states.json` 的状态引用区分用途；仅状态专用的图片不得进入普通切图列表、普通资源数量、画布命中或 Vue 静态页生成。若同一资源同时被普通 placement 和状态引用，仍保留其普通资源身份。普通资源统计与新增状态资源统计分别记录，不改变旧统计字段的含义。

导入时对「声明但未导出」的状态计算缺失警告；对 `states.json` 引用未知 `assetId`、资源路径越界、资源文件丢失或实际 SHA-256 不符，视为 Bundle 数据损坏并拒绝导入或标为不可用，不把它伪装成业务上的正常缺失。状态资源字节校验要有明确的耗时和取消反馈。

### 6.10 看稿运行模型

给当前会话增加只读的组件状态事实；运行中的 `currentStateId` 是临时预览状态，不写回不可变 Bundle。用独立的纯函数按 `{componentId, currentStateId, event}` 查找转换并返回下一个状态；没有规则时保持原状态并显示当前事件无映射。组件切换、关闭状态面板或重新打开文件时重置到初始状态，避免把上一个组件的状态带过来。

状态图片按 Bundle 资源引用按需从 OPFS 读取并生成 object URL；组件切换、文件关闭、预览卸载时撤销 URL。资源加载中保留稳定预览尺寸；资源缺失显示组件名、状态名和原因，不继续显示上一帧。对禁用态只允许审稿控件直接切换查看，不让预览按钮产生普通 `click` 转换。为按压态使用指针捕获或等价的取消处理，并单独测试鼠标移出、触屏取消和键盘触发。

看稿显示开关属于本机 UI 偏好；建议放在现有 `LocalBundlePreferences` 中，保存和恢复仍走 `bundleRepository.updatePreferences`。Bundle 中的转换规则是交付事实，本机开关只控制是否显示；关闭时不改动数据、审计结果或资源缓存。

## 7 发布基线与其他桌面功能

Windows 发布当前已在 `tauri.conf.json` 中启用 NSIS 并声明 runner 资源；下一步应核对 Tauri 配置与 Cargo 版本、release 编译、打包后的实际资源路径，再在无开发环境变量、无本机 Python 虚拟环境的独立 Windows 机器验证安装、转换、取消、看稿和打开产物。`runner.rs` 的当前工作区改动把 `runner_file_name` 定义在 `from_app` 内，却通过 `Self::runner_file_name()` 调用；这看起来需要在 release 编译中核对并可能调整，尚未运行编译验证。不能仅凭配置存在或 `tauri:build` 成功认定发布可用。

任务持久化建议在应用数据目录保存有限条任务摘要、状态、时间、输入显示名、输出目录及诊断，不把 PSD 原件或大量日志复制入数据库。启动时将中断的 `running` 任务标为中断，验证原输出是否仍存在；最近任务应可重新打开产物或复用参数。保存参数预设时将路径与通用转换选项分开，防止把旧输出路径误用于新任务。

批量转换、拖入与系统文件关联都应在首个安装版和状态流程稳定后，根据实际单次交付 PSD 数量决定是否实施。

### 8.1 逐阶段审查门槛

实施时每阶段先交付证据，再进入下一阶段；本次文档审查不授权代码修改。

| 阶段 | 逐项检查 |
| --- | --- |

| C 契约 | 协议 1 保持原样、协议 2 样例、旧新 Bundle 样例、状态缺失与资源损坏样例 |

### 8.2 失败与回退规则

- 某个已确认状态的像素导出失败：在 `states.json` 保留状态声明，省略资源 ID，记录警告并允许交付；预览显示缺失，不显示旧图片。
- 源身份无法确认、计划结构错误或整包校验失败：不产生成功的状态 Bundle，也不自动降级为旧包。用户可明确关闭开关重新走旧流程。
- 新包资源损坏或路径不安全：必须按导入错误处理；关闭看稿显示开关不能绕过安全校验。
- 旧客户端无法理解 Bundle `1.1.0`：使用新版看稿台打开；功能关闭时继续生成旧 `1.0.0` 包。
- 启用状态模式但没有确认组件：新包可有空 `states.json`，覆盖结果为未定义，不得显示「完整」。
